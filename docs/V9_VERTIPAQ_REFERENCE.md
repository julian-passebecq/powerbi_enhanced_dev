# V9.4 VertiPaq and optimization evidence

PbiBench independently implements a bounded reader for SQLBI's documented VPAX statistics format, an original metrics workspace and optimization suggestions, and a fixed public-DMV capture adapter. It retains the TE2 model engine and standalone DAX Studio boundary.

## Public input and provenance

- [SQLBI VPAX format](https://docs.sqlbi.com/vertipaq-analyzer/) documents a ZIP containing `DaxModel.json`, `DaxVpaView.json`, and optional `Model.bim`. Only the statistics part is read; no ZIP entries are extracted to disk and no embedded TOM metadata is loaded into an editor.
- [Dax.Vpax 1.12.1](https://www.nuget.org/packages/Dax.Vpax/1.12.1), published 2026-04-16, identifies public source commit `f3a12773cbb386ac974a13083e451331e9f7ce3d` and MIT licensing. PbiBench's compatibility fixture is upstream's public Contoso VPAX with its MIT notice retained in `tests/PbiBench.Adapters.Tests/TestData/VertiPaq/`. No proprietary editor code, assets, optimizer output or internal formats are used.
- The pinned public [column model](https://github.com/sql-bi/VertiPaq-Analyzer/blob/f3a12773cbb386ac974a13083e451331e9f7ce3d/src/Dax.Metadata/Column.cs) defines column bytes as data segments + dictionary + attribute hierarchy structures. Its [table model](https://github.com/sql-bi/VertiPaq-Analyzer/blob/f3a12773cbb386ac974a13083e451331e9f7ce3d/src/Dax.Metadata/Table.cs) adds user hierarchies and relationship-end structures. PbiBench uses those distinct components and never repeatedly adds dictionary bytes for each segment or partition.
- [Extraction properties](https://github.com/sql-bi/VertiPaq-Analyzer/blob/f3a12773cbb386ac974a13083e451331e9f7ce3d/src/Dax.Metadata/ExtractorProperties.cs) distinguish data statistics and DirectQuery/Direct Lake scope. Relationship key counts remain unavailable unless collection coverage is explicit. Segment temperature, residency and last access stay nullable; they are not evidence that a model object is unused in reports.

The reader supports model schemas 1.0 through 1.9, UTF-8 BOM, legacy name objects, string names, `$id`/`$ref` and `$values` collections. It rejects unknown schema versions, ambiguous statistics entries, duplicate/cyclic/missing references and invalid metric values. Limits are 256 MB archive, 64 MB expanded JSON, 64 archive entries, JSON depth 128 and 500,000 JSON values. Cancellation applies to file reads and parsing. Unknown numeric metrics remain null; a total is unavailable if any component is unavailable.

## Live metrics

[Microsoft's Analysis Services DMV documentation](https://learn.microsoft.com/en-us/analysis-services/instances/use-dynamic-management-views-dmvs-to-monitor-analysis-services?view=sql-analysis-services-2025) describes the public `$SYSTEM` rowsets and endpoint/permission limits. PbiBench exposes no free-form DMV execution API. The capture adapter accepts a typed server/database/options request and can issue only its eight fixed metric rowsets: model, tables, columns, partitions, relationships, storage tables, storage columns and storage segments.

Each capture owns an independent TOM session and catalog. A per-command cancellation worker is joined before reader disposal or reuse. Capture timeout covers the entire operation; retained rows and cells are bounded. Denied, unavailable or truncated rowsets yield explicit partial results, and truncated metric data is discarded instead of producing misleading totals. No data scans, cache commands, refresh, deployment, writes or model-editor session reuse occur. The existing DAX query service continues to reject `SELECT`, XMLA and model-change input.

Storage identifiers are reconciled with captured TMSCHEMA metadata; changed identities are omitted. Attribute hierarchy cardinality follows the public [SQLBI DMV extractor](https://github.com/sql-bi/VertiPaq-Analyzer/blob/f3a12773cbb386ac974a13083e451331e9f7ce3d/src/Dax.Model.Extractor/DmvExtractor.cs) convention of subtracting its three internal hierarchy entries. Sequential DMV captures are not an atomic snapshot; Direct Lake/residency and engine changes can affect coverage. The UI binds imported object names to the current model only after explicit association and invalidates binding/evidence on model fingerprint or connection changes.

## Benchmark evidence and optimization

The cockpit joins original memory/RI/residency suggestions with supplied BPA/test signals, retaining source, category, risk and evidence. Memory suggestions require profiling and representative benchmarks; none automatically deletes objects, changes types or disables MDX. Existing BPA fixes remain in their guarded preview workflow.

The A/B benchmark runs exact baseline and candidate DAX alternately, 1–10 iterations per query, using independent query sessions and normal cancellation. It never clears caches or starts a trace. Evidence records context, local metadata fingerprint, query hashes, each execution, result hashes, row counts, failures and client elapsed time including connections/result transfer. It rejects stale query/target/revision/identity/timestamps, malformed or oversized results, empty result collections, truncation and type/value/order differences before accepting a timing comparison. FE/SE and cache-controlled timings are unavailable; medians and percentage changes are observations under current load, not universal optimization claims. Canceled or model-stale runs cannot become accepted evidence. JSON export is atomic and contains no transport credentials.

[DAX Studio BENCHMARK documentation](https://daxstudio.org/docs/features/command-line/commands/benchmark-command/) states that its default cold runs clear the cache. This workspace does not call that existing bridge overload. Deep trace/cache-controlled performance work remains in standalone DAX Studio through explicit specialist workflows. [DAX Studio VPAX extraction options](https://daxstudio.org/docs/features/command-line/commands/vpax-command/) can enable data statistics, so this workspace's live capture uses the explicit metadata-only DMV path instead.

Automated verification includes the public real VPAX fixture, legacy/reference/BOM parsing, numeric/missing/partial metrics, DirectQuery statistics coverage, independent fixed-DMV sessions, cancellation/timeout/permissions, benchmark provenance/equivalence/failure and credential-free evidence export. These tests are not evidence of successful extraction from a populated live model on this machine; the prior endpoint probe found no visible catalog, and no test model was deployed to manufacture one.
